# ADR-004: Patch → standalone module migration

Status: **Core migration implemented**: all business logic, chat commands, world-tick
reconciliation, config, and both behavior-override points run as a standalone AzerothCore module
with zero changes to mod-playerbots source. **Not yet done**: GM diagnostic commands
(`testbotpool`, `lfgstate`, `pathcheck`, `pathcheckfrom`, `tpbot`) from the patch era, and a
confirmed live end-to-end dungeon run through the module (registration is confirmed working;
a full run is not, as of this writing).

## Context

The original design was a flat patch against a pinned mod-playerbots commit, regenerated by hand
from a private `dungeon-lead` branch whenever upstream moved (see the old README "Maintainer
workflow", now removed). This worked, but had a structural cost that showed up concretely: a
scheduled `upstream-compat.yml` check caught the patch silently failing to apply roughly once a
month as upstream drifted (tracked in issue #2) — not a bug in the patch itself, just two
independent commit histories that happened to intersect less and less cleanly over time. Fixing it
each time meant re-deriving a flat diff by hand against whatever upstream had become.

The deeper problem wasn't the specific breakage — it was that there were, structurally, **two
codebases to keep synchronized**: the "real" source (a branch inside a live mod-playerbots
checkout, not published anywhere) and this repo's own `src/DungeonLead/` mirror plus the generated
patch. Every update needed care that both stayed byte-identical. That's what this migration
removes.

## Rejected: automate patch regeneration instead

Before concluding a module was possible at all, the cheaper-looking option was considered: keep
the patch, just script the regeneration (rebase branch, re-diff, bump pinned commit) so it's one
command instead of a manual process. Rejected — it would have removed the manual tedium but kept
every structural problem: two codebases, a pinned commit that can still silently drift between
scheduled checks, and no way for the build itself to catch a break before a human runs the script.

## Accepted approach: patchless registration via existing C++ access rules

mod-playerbots exposes no plugin API for third-party Strategies/Actions/Triggers — `AiObjectContext`
and its ten per-class subclasses (`WarriorAiObjectContext`, ...) hold their registries as private
(base class) or public (per-class) static `SharedNamedObjectContextList<T>` members, populated once
at startup from hardcoded `Build*Contexts()` functions. Investigation (reading the actual
mod-playerbots source directly, not assuming) found:

- The **ten per-class registries are public static members** — reached directly, no trick needed.
  Every real bot is built from its own class's context (`AiFactory::createAiObjectContext` switches
  on `CLASS_*`), never the base one — a registration reaching only the base lists would reach no
  bot at all. This is why the module registers into all eleven lists (base + 10 classes), not just
  one.
- The **base `AiObjectContext`'s four registries are private**, but their addresses are reachable
  without undefined behavior via the explicit-instantiation access technique ([temp.explicit] /
  [class.access.general] in the C++ standard: naming a private member in an explicit template
  instantiation argument is exempt from access control). See `src/DungeonLeadAccess.h`. This is a
  well-known idiom, independently implemented here — not copied from anywhere.
- `SharedNamedObjectContextList<T>::Add()` appends a whole new `NamedObjectContext<T>` and merges
  its `creators` map into the shared one with plain `map[key] = value` assignment — so **registering
  a key that already exists overwrites it**, not just adds a new one. This turned out to matter a
  lot (see "The two override points" below).
- Registration happens from a `WorldScript::OnUpdate`, latched to run once on the first world tick
  — guaranteed to fire after mod-playerbots' own `AiObjectContext::BuildAllSharedContexts()` and
  `PlayerbotAIConfig::Initialize()` have already run, with no module-load-order race to reason
  about.

### Config: independent, not shared

Rather than extend mod-playerbots' `PlayerbotAIConfig` (which would mean patching its header),
`DungeonLeadConfig` (`src/DungeonLeadConfig.h`) is its own lazy singleton, reading the exact same
`AiPlayerbot.DungeonLead.*` keys directly via `sConfigMgr`. Same keys, same defaults, ships its own
`conf/mod-dungeon-lead.conf.dist` — AzerothCore's module system merges it automatically.

### Chat commands: a module-owned always-on strategy, not an edited one

The patch added `startdungeon`/`stopdungeon`/`canarytest` as `TriggerNode`s inside
mod-playerbots' own `ChatCommandHandlerStrategy`. The module instead defines its own tiny
`DungeonLeadCommandsStrategy` (a `PassThroughStrategy`, same base `ChatCommandHandlerStrategy`
uses) carrying exactly those three `TriggerNode`s, registered under its own name
("dungeon lead commands") and injected into `sPlayerbotAIConfig.nonCombatStrategies` /
`randomBotNonCombatStrategies` at startup — both are plain public `std::string` fields, no patch
needed to touch them. Every bot's default strategy set picks it up because the injection runs
before any bot can plausibly have logged in.

### GM commands: a new root, not an edited one

Likewise, `.playerbots testbotpool`/`canarytest`/etc. in the patch extended mod-playerbots' own
`playerbots_commandscript`. The module instead registers its own `CommandScript` under `.dungeonlead`
(`src/DungeonLeadCommandScript.cpp`) — AzerothCore's `CommandScript` registration is already a
patchless extension point; a new root needs no edit to existing command tables. Only `canarytest`
is ported as of this writing (see "Known gaps").

## The two override points

Two places in the original patch changed **existing** mod-playerbots behavior rather than adding
something new — not reachable by a plain registry append:

- **`UnknownDungeonTrigger::IsActive()`** (key `"unknown dungeon"`, in `TriggerContext`) hands the
  bot back to the real player whenever it's in a dungeon, which would otherwise keep undoing an
  active "dungeon lead"/"grind" session.
- **`FormationValue::Load()`** (key `"formation"`, in `ValueContext`) doesn't know a `"leader"`
  formation (follow the new bot leader instead of the real player).

Both target methods are `virtual` (confirmed by reading `Trigger.h` / `Value.h` directly), and the
relevant internal state (`ManualSetValue<T>::value`, `PlayerbotAIAware::botAI`) is `protected`, not
private. This made the fix mechanical: a subclass of each
(`DungeonLeadAwareUnknownDungeonTrigger`, `DungeonLeadFormationValue` — both in
`src/DungeonLeadOverrides.h`) that handles the new case and delegates to the base implementation
for everything else, registered under the **same key** mod-playerbots already uses. Because the
module's registration runs after mod-playerbots' own (first world tick vs. startup), the
map-overwrite behavior described above means this is a straight replacement, not a conflict.

## A real bug found during migration: duplicate symbols, not just duplicate source

Porting `src/DungeonLead/` (unchanged business logic, 12 files) into the module while the original
patch was still applied to the live mod-playerbots checkout produced a **One Definition Rule
violation**, not just redundant code: both copies declare the exact same unnamespaced class names
(`DungeonLeadStrategy`, `DungeonLeadNextAction`, ...) and free functions (`DungeonLead::
GuardActiveSessions()`, ...), so both `.o` files export identical mangled symbols into the same
`libmodules.a`. Confirmed directly with `nm -C` on both object files before drawing any
conclusion. The build still succeeded — a static archive silently resolves a duplicate strong
symbol to whichever member the linker needs first — which meant it was genuinely **undefined which
copy was actually running**, making any test result meaningless until fixed.

Commenting out the old patch's registration call-sites (the `creators[...]` lines across five
registry headers, plus the three `OnUpdate` hook calls) was **not sufficient** — the old `.cpp`
files were still compiled and still exported the colliding symbols, available for the linker to
pick regardless of who still referenced them. The actual fix: the old `src/Ai/Base/DungeonLead/*.cpp`
files in the mod-playerbots checkout were wrapped whole in `#if 0 ... #endif` — left on disk,
compiling to nothing, defining nothing. Verified with `nm -C` again post-rebuild: zero `DungeonLead`
symbols from the old location. The module's copies are now the sole source of these symbols.

(The patch's other six non-duplicated touch points — `Formations.cpp`'s `"leader"` case and
`LfgTriggers.cpp`'s bypass among them — were left active and harmless through this phase, since
they aren't class/symbol duplicates and the module's own override versions didn't exist yet at
that point in the migration.)

## Verification

Registration is confirmed via `Playerbots.log` on every restart:
```
[DungeonLead] module loaded, world tick reached - registering...
[DungeonLead] registered into base + 10 per-class contexts, 'dungeon lead commands' added to default non-combat strategies
```
with zero entries in `Errors.log` attributable to the module, across several rebuild/restart
cycles (PoC → full port → override points).

A full live run (whisper `startdungeon` or an LFG-formed bot-only group → route walked → bosses
killed → session completes) has **not** been confirmed as of this writing. `DungeonLead::
TriggerTargetedTest()` (the same function `.dungeonlead canarytest <lfgId>` calls) was used as a
temporary self-triggered check from the module's own `OnUpdate` (retried every 5 minutes) during
development to avoid depending on a live tester or on SOAP access, which was unavailable in that
environment. That temporary self-trigger is not part of this module's shipped code.

## Known gaps (as of this writing)

- GM diagnostic commands from the patch era — `testbotpool acquire/status/release/run`,
  `lfgstate`, `pathcheck`, `pathcheckfrom`, `tpbot` — are not yet ported to `.dungeonlead`. The
  underlying `DungeonLead::`/`DungeonTestBotPool::` functions they'd call are already present
  (ported unchanged); only the command bindings are missing.
- `RandomPlayerbotMgr::OnPlayerLogin`'s one-line AddClass-bot classification fix (ADR-003) — needed
  only if `DungeonTestBotPool` is used — has no patchless equivalent found yet. It's a single `else
  if` branch in an existing function body, the same category of problem as the two override points
  above, but neither target is `virtual`. If this turns out to matter in practice, the two honest
  options are: the one remaining small patch, kept deliberately minimal and documented here, or an
  AzerothCore `PlayerScript::OnPlayerLogin` hook that runs after mod-playerbots' own and corrects
  the misclassification from outside rather than preventing it.
- No build-time CI for the module (a GitHub Actions compile check was considered and declined for
  cost/self-hosted-runner reasons). Lower priority than before this migration, since there's no
  more pinned-commit drift for a scheduled check to catch; a compile break from a mod-playerbots
  update would now surface the next time anyone builds, not silently.

## Explicitly deferred

- Removing the pre-migration patch-based state entirely from history isn't planned — it remains
  recoverable from this repo's own git history (the patch file and the old `src/DungeonLead/`
  mirror were simply removed going forward, not scrubbed from past commits).
