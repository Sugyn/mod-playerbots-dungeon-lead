# ADR-001: L1.4 Capability Scenario Framework — architect pass

Status: **Proposed, not implemented.** Architect pass only, per the roadmap's four-pass workflow
(architect → implementer → reviewer → fix+test). Written to be reviewed and revised before any
code exists, not after.

## Context

L1.3 (`startdungeon test`) shipped as one live end-to-end smoke test: start a real run in a real
dungeon, wait for a terminal `RunOutcome`, report a result. That's the right *first* thing (per the
roadmap: "do not build a full provisioning framework, implement one live test command first"), but
it has an inherent limit — a single full-dungeon run mixes together navigation, party coordination,
pull planning, marking/CC, and encounter completion into one pass/fail signal. A failure tells you
"something went wrong somewhere in a 20-minute run," not which subsystem.

L1.4's stated purpose is exactly that: isolate testing by domain (Party Coordination, Marking/CC,
Pull Planning, Encounter, Recovery) so a failure points at a subsystem, not a whole dungeon.

## The constraint this ADR has to work around

The roadmap's own L3/L4 (Objective Graph, World Model, Planner) don't exist yet — the engine is
still `DungeonRouteStep[]` + `stepIndex`, and `DungeonLeadNextAction`/`DungeonLeadMarkAction`/the
multiplier all read live world state directly (nearby creatures, group members, mana) rather than
through any testable intermediate representation. There is no seam to inject a synthetic "world
state" and observe a decision in isolation the way a unit test normally would.

Building that seam properly is L3/L4-sized work. Concluding "so build L3/L4 first" would violate
the roadmap's own explicit rule ("do not start the Objective Graph rewrite" before L1 exists) and
its reasoning (an untested core rewrite on top of an untested core rewrite is the exact opposite of
what the test harness is supposed to protect against).

## Proposed MVP scope for L1.4

Not a generic scenario framework yet. A **narrower, honest MVP**: reuse the real production code
paths (no new abstraction layer), but let a GM command jump straight to the specific decision point
instead of walking a whole route to reach it, and print what the production code actually decided.

```text
.startdungeon scenario cc <lfgId>       teleport near a known CC-eligible pack, invoke
                                          DungeonLeadMarkAction directly, report moon target chosen
.startdungeon scenario pull <lfgId>     teleport near a known boss, report what DungeonLeadNextAction
                                          /the multiplier would currently decide (pull / wait / why)
.startdungeon scenario party <lfgId>    report GroupInCombat/GroupResting/HealerManaLow/GroupTooSpread/
                                          MasterUnavailable's current values and why, without acting
```

Each scenario:
- requires a manually-prepared party in the target dungeon (same constraint L1.3 accepted - no
  automatic provisioning here either);
- calls the *actual* production function (`DungeonLeadMarkAction::Execute`,
  `DungeonLead::GroupTooSpread`, etc.) — never a reimplementation or a mock, so a scenario passing
  actually means the shipped code path was exercised;
- reports a decision + the "why" (which config threshold / which member / which distance), not
  just pass/fail — closer to `startdungeon status` than to a pass/fail test.

## What this deliberately does NOT do

- No synthetic/mocked world state. Every scenario runs against a real instance with a real party -
  narrower than a full dungeon run, but not isolated from AzerothCore's own state.
- No scenario seed / reproducibility model (roadmap L1's "Reproducible Test Scenario," section 7 of
  the v2 roadmap) yet - that needs the World Model to define what a scenario's inputs even are.
- No automated pass/fail assertion. A human (or `startdungeon test`'s own terminal-outcome check)
  still judges whether the reported decision was correct - this is an *observability* tool, not a
  test-runner, until there's a real expected-value contract to assert against.
- No `tests/` directory, no `run_dungeon_tests.py`/`compare_results.py` scaffolding from the
  roadmap's suggested layout (section 4) - premature before even one scenario type is proven useful.

## Why this is still worth doing before L3/L4

It gives Claude Code (and a human tester) a way to check "did the CC/pull/party-spread logic
change do what I think" in under a minute, against the real code, without a 15-minute dungeon
clear - closing the actual gap L1.4 exists to close - without inventing new architecture that would
need to be thrown away once the Objective Graph lands.

## Open questions (for review before implementation starts)

1. Is three scenario types (cc/pull/party) the right starting set, or should the first
   implementation be a single one (probably `party`, since `GroupTooSpread` naming the offender was
   the most recent real bug) to validate the command-dispatch pattern before building the other two?
2. Should scenario output go through the same `RecordEvent` CSV, tagged with a `scenario` event
   type, so it's queryable alongside real runs - or is that conflating two different kinds of data?
3. `cc`/`pull` scenarios need "a known CC-eligible pack" / "a known boss" near the party's current
   position - do we require the tester to already be standing near one (simplest, matches L1.3's
   "no auto-provisioning"), or look one up from `data/dungeon_routes.csv` for the current instance?

## Decision

Not yet made - this ADR is the artifact to review/revise before the implementer pass begins.
